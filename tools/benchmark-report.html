Why localhost hides the problem

The old sender sent one chunk, then blocked on recv() for that chunk's ACK before sending the next — throughput capped at roughly chunk_size / RTT, not chunk_size / transmit-time. On localhost, RTT is near zero, so the cap is invisible. Over any real link the cap dominates completely, independent of file size — which is exactly what the "before" data below shows: throughput at a given latency barely moves between a 5 MB and a 200 MB file, because it was never bandwidth-bound to begin with.

The chunk-size tradeoff

Bigger chunks help for the same reason a bigger window does: with window fixed at 16, going from 64 KB to 1 MB chunks takes bytes-in-flight from 1 MB to 16 MB, so fewer round trips are needed to move the same file — throughput roughly triples from 64 KB to 256 KB and triples again by 1 MB. But it's not a free win: the resume grain gets coarser along with it. A hash mismatch or an interrupted transfer now costs re-sending up to a full 1 MB chunk instead of 64 KB, and the in-memory queues (BoundedQueue, sized to hold window chunks each) get proportionally bigger too. Pick chunk size for the network you're actually deploying on, not just for the biggest number in a benchmark.

What's actually the bottleneck (added 2026-07-31)

The first version of this report guessed that 0 ms/window=32 plateauing around ~20 MB/s was a disk-read + SHA-256 + loopback ceiling. That guess was wrong, and measuring it properly — timestamping each pipeline stage in isolation via --bench — found the real number. For a 200 MB transfer at 64 KB chunks (3,200 chunks, window 32, 0 ms simulated latency):

StageIsolated throughput
Disk read~500-650 MB/s
SHA-256 hash~600-700 MB/s
Network send()~140-190 MB/s
Ack recv()~2.9 ms/ack — 9.36s of a 9.6s transfer

None of read, hash, or send were the ceiling — the ack-listener thread's blocking recv() calls were, and they stayed the ceiling even at 0 ms of simulated latency, because there's still a real per-syscall/per-round-trip cost on this machine's loopback stack that the latency proxy never touches. With 3,200 acks to receive one at a time on a single thread, ~2.9 ms each adds up to ~9.3 of the 9.6 total seconds — the other three stages were essentially free by comparison, just running in parallel on other threads while the ack listener was the real critical path.

This is exactly why bigger chunks helped so much: going from 64 KB to 8 MB chunks isn't really "sending more data per call," it's 128× fewer acks for the same 200 MB — directly cutting the dominant cost. Extending the chunk-size sweep to the protocol maximum (8 MB, 25 acks instead of 3,200) reached ~220-290 MB/s, roughly 10× the 64 KB result — see Chart 3, now extended past 1 MB. The remaining lever this doesn't reach — cutting the per-ack cost itself, e.g. cumulative acks instead of one-per-chunk — would be a real protocol redesign, not attempted here.

Method

Localhost RTT is near zero, so testing "as-is" would show no difference. Latency was simulated with a small TCP proxy (tools/latency-proxy.js) that delays only the receiver→sender (ACK) direction by a fixed amount — matching how a real network adds latency without corrupting byte ordering or forcing the receiver's own thread to block.

An earlier attempt used a Sleep() inside the receiver's single thread before each ACK. That's equivalent for the stop-and-wait engine (only one chunk is ever outstanding at once), but for the pipelined engine it serialized every ACK through one blocking point regardless of window size — capping receiver throughput at 1/delay chunks per second and making pipelining look far less effective than it is. Chart 1's "before" series used the Sleep() method (valid for that engine); its "after" series and all of Chart 2 used the proxy.

Addendum — TLS (added 2026-07-31)

Every connection is now TLS-encrypted by default (protocol v11): the receiver generates a fresh self-signed certificate on every start, and the sender accepts it without checking it against a trust anchor (SSL_VERIFY_NONE). That protects the transfer against passive eavesdropping on the wire, not against an active machine-in-the-middle on the very first connection to a given receiver — there's no established identity to check the certificate against. A matched-pair --no-tls flag exists on both sides for local debugging/benchmarking; a sender and receiver with mismatched TLS settings fail the connection cleanly rather than hang.

Ran 200 MB @ 0/50 ms RTT with and without TLS at three chunk sizes. At 64 KB (ack-dominated, ~8-13s transfers — long enough to average out noise): TLS-on 24.1/15.5 MB/s vs. TLS-off 22.7/14.1 MB/s — TLS came out slightly faster, which is itself the signal: any real encryption cost is smaller than normal run-to-run variance. At 1 MB and 8 MB chunks the transfers are very short (under 1-2.5s), and a first pass showed TLS-off oddly slower by 2-3× at large chunk sizes — physically implausible for encryption to speed anything up, so it was re-run rather than reported at face value. The re-run landed both configurations in the same 114-245 MB/s band with no consistent direction either way, confirming the first result was noise from this being a shared, actively-used machine, not a real TLS penalty. Believable result either way: AES-GCM is hardware-accelerated (AES-NI) on essentially every x86-64 CPU since ~2010, so actual encryption cost should be small relative to everything else going on. Not a proper multiple-trial statistical comparison — see limitations — so "no measurable overhead" is directionally credible, not a precise number.

Bonus effect of adding TLS: linking against -static (already needed for the pthread runtime — see the pipelining work above) turned out to statically link OpenSSL too, despite CMake's own configure log reporting it had found the dynamic import library. Verified via objdump -p sender.exe | grep "DLL Name": both exes now depend on nothing but standard Windows system DLLs (KERNEL32, msvcrt, WS2_32, ADVAPI32, CRYPT32, USER32) — no MSYS2 DLLs of any kind need to be on PATH to run these anymore, closing out the last runtime dependency from the original pipelining work.

Known limitations

  • Chunk-size sweep only ran at one window size (16) and one file size (200 MB). Window and chunk size interact — both change bytes-in-flight — so this isolates neither perfectly; treat Chart 3 as "chunk size with window held at a realistic default," not a pure isolated variable.
  • A hash mismatch is now fatal to the session instead of retried in place — pipelined chunks may already be in flight past a bad one, so the session disconnects and the existing resume protocol picks up from the last durable chunk on the next run. Verified working, but it means a single corrupted chunk costs a reconnect, not a resend.
  • Neither disk, hashing, nor bandwidth was ever the ceiling at 64 KB chunks — the ack-listener's recv() calls were (see "What's actually the bottleneck" above), even at 0 ms simulated latency. This means the throughput numbers in this report are a floor, not a hardware ceiling — a genuinely bandwidth-constrained real network, or a machine with a slower loopback stack, would show different numbers, and the true disk/network limits of this specific machine are still unmeasured.
  • Still Winsock2-only, still one connection per process. Cross-platform sockets and multi-transfer concurrency were explicitly deferred, not attempted here.
  • Single machine, one test pass per condition. No repeated trials/variance reported — treat these as one representative run each, not statistically averaged. This is exactly why the TLS-overhead comparison can only say "no clearly measurable difference," not give a precise percentage.
  • TLS protects confidentiality, not receiver identity. The self-signed, freshly-generated-per-run certificate means a passive eavesdropper on the network can't read the transfer, but nothing stops an active attacker from impersonating the receiver on the very first connection — there's no certificate pinning or out-of-band fingerprint check.
